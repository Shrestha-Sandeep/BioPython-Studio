# P01 — A scientific Python program

**Outcome:** run a small script that records a specimen, performs a unit-aware calculation and prints an interpretable result. This chapter covers competency numbers **001–007**. Four executable activities are defined in `../activities/foundations.json`.

## 1. A program is a reproducible instruction

At the microscope, you may write down a sample label, an image identifier and a measured value. In Python, the same record becomes data that can be checked, reused, reformatted and eventually combined with other measurements. Python executes statements from top to bottom. A line is not executed just because it appears in an editor: you must run it.

```python
sample_id = "N2_plate03"
fields_counted = 6
print(sample_id)
print(fields_counted)
```

**Predict** the output before running. Which lines merely store values? Which lines display them? In a normal script, an assignment such as `fields_counted = 6` does not print anything. `print()` explicitly creates text output; the editor must show that output instead of inventing a result.

An interactive notebook can automatically display the result of its last expression. A script does not necessarily do so. Remember the difference: a notebook has state from previously executed cells, while a program run in a clean process starts without prior variables. The most reliable scientific analysis should be reproducible from the top on a fresh kernel.

## 2. Variables are labels for values

A variable name should state what the value represents. Compare `a = 6` with `fields_counted = 6`. Both are valid Python, but only one explains the calculation in a notebook you open months later.

Python values have types. The integer `6` is an `int`; a measured value `2.5` is usually a `float`; `True` is a `bool`; and `"N2_plate03"` is a `str`. Use `type(value)` when uncertain. A bool is not a measured fluorescence value: it answers yes/no.

```python
pixels_per_micrometre = 4.0
region_width_pixels = 48
width_um = region_width_pixels / pixels_per_micrometre
print(width_um)
```

The calculation returns **12.0**, but the computer does not know that the output is micrometres unless you store the calibration assumption in the variable names and metadata. If the pixel scale is wrong, correct Python produces a wrong physical answer. Units are part of scientific meaning, not part of Python's number system.

**Prediction check:** If `pixels_per_micrometre` increases from 4 to 8 while the pixel width stays 48, does the physical width increase or decrease? Explain before running.

## 3. Errors reveal the first failed assumption

Most new programmers fear error messages unnecessarily. A traceback tells you where an exception arose and what Python was trying to do. The final line gives the exception type and explanation; a line above identifies the failing statement.

```python
region_width_pixels = 48
print(region_width_pixel)
```

This raises `NameError` because the singular name has not been defined. Fixing the spelling is better than suppressing the error. Similarly, dividing by zero raises `ZeroDivisionError`; indexing a list beyond its length raises `IndexError`. Later lessons will teach when and how to handle expected failures with explicit rules.

Get help through `help(print)`, the Python documentation, and experimentally small code snippets. Ask: *What type does this function expect? What does it return?* Read documentation rather than memorizing every API.

## 4. Notebook state is a scientific risk

Consider these three cells executed in order:

```python
# Cell A
field_count = 4

# Cell B
double_count = field_count * 2

# Cell C
print(double_count)
```

If you later change Cell A to `field_count = 8` but rerun only Cell C, it can still print the old `double_count`. A notebook stores values that were calculated earlier; changing a cell's text is not the same as recomputing its dependent results. A clean restart and Run All is a useful reproducibility check.
